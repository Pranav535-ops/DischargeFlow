# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

DischargeFlow is a hospital discharge management system: a FastAPI backend (`backend/app/`) on SQLAlchemy + PostgreSQL, and a Vite + React 19 frontend (`frontend/`). It was scaffolded on the Emergent platform (`.emergent/`, Emergent Auth). Product requirements are in `memory/PRD.md`, the user-facing overview is `README.md`, and every endpoint with the permission it requires is in `docs/api.md` (update it when adding or changing a route). **The target architecture and Phases 1–6 are in `docs/architecture/ADR-001-production-architecture.md`; ADR-002 (`docs/architecture/ADR-002-hospital-readiness.md`) validates it against real-hospital use and plans Phases 7–9.** Phase 1 (modular backend + Postgres + Alembic + tests) and Phase 2 (hardened sessions, DB-backed permissions, tenant RLS, PHI encryption, tamper-evident audit) are done. Phase 2 kept the Emergent Google login rather than switching to Cognito. Phase 3 (governed AI layer: LLM gateway, de-identification, structured summaries with provenance, golden-set evals, tool-calling assistant) is done except the async outbox/SQS worker (item 11). Phase 4 (Terraform for AWS, deploy pipeline, observability, runbooks) is written and validated but not applied: there is no AWS account, so production still runs on Vercel + Neon. Phase 5 (Vite + TanStack Query + URL routes, Playwright E2E, read-only FHIR R4, admin AI insights) is done. Phase 6 (live notification stream over SSE, operational metrics, import-linter/mypy/Dependabot gates, inbound HL7 v2 ADT) is done. In ADR-002's Phase 7 (pilot readiness), item 1 is done: approval-gated sign-up, task ownership, claim permissions, write and PHI-read audit coverage.

`project_implementation_plan.md` predates the repo audit (it assumes Node and microservices) and is superseded by ADR-001. `project_overview.md` describes a different project (SkillGraph V2). `test_result.md`, `test_reports/` and `branches.txt` are leftovers from the Emergent platform. Ignore all of them.

## Commands

Backend (run from `backend/`, with `venv` active):
```bash
pip install -r requirements.txt
python -m app.cli migrate            # alembic upgrade head + encrypt any plaintext PHI (use this, not bare alembic)
python -m app.cli seed               # idempotent demo patients; refuses in production without --force
python -m uvicorn server:app --port 8000 --reload
python -m pytest                     # full suite, in-memory SQLite
ruff check .                         # lint gate in CI (errors only, see ruff.toml)
lint-imports                         # module-boundary contracts in .importlinter (CI gate)
mypy                                 # type check of the modules listed in mypy.ini (CI gate; app.ai and app.chatbot not yet)
python -m app.cli rewrap-deks        # PHI KEK rotation step, see docs/runbooks/rotate-secrets.md
python -m app.ai.evals               # golden-set AI evals on the mock adapter (CI gate); --provider anthropic --model claude-haiku-5-5 for a real model
python -m pytest tests/test_discharge_workflow.py::test_full_discharge_happy_path   # single test
alembic revision --autogenerate -m "describe change"   # after editing models; review the generated file
```
Run the suite against Postgres by setting `TEST_DATABASE_URL=postgresql+asyncpg://...`. CI runs both SQLite and a Postgres 16 service. Tenant-isolation (RLS) tests are marked `requires_postgres` and only run against Postgres. `tests/test_platform.py` shells out to Alembic to check `upgrade` → `check` (model/migration drift) → `downgrade`, and upgrades real 0001-era data through `app.cli migrate`. A model change without a migration therefore fails the tests.

Frontend (from `frontend/`, Node 22):
```bash
npm ci
npm run dev                          # Vite on :3000, proxies /api to http://localhost:8000 (override with VITE_DEV_API)
npm run build                        # to frontend/build (the directory Vercel, the Dockerfile and deploy.yml expect)
npm test                             # Vitest + Testing Library
npx eslint .                         # lint gate in CI
npx playwright test                  # E2E: starts the backend (mock AI, dev login) and `vite preview` itself
```
For E2E locally, set `E2E_PYTHON` to the backend venv's python (absolute path on Windows), and `PW_CHANNEL=chrome` to use an installed Chrome instead of downloading Playwright's Chromium. `E2E_DATABASE_URL` picks the database (default: a throwaway SQLite file). `VITE_BACKEND_URL` (or the legacy `REACT_APP_BACKEND_URL`) points the built app at another API origin; empty means same-origin `/api`.

Full stack: `docker compose up --build` starts Postgres, runs a one-shot `migrate` service, then the backend (with `SEED_ON_STARTUP=true`) and the frontend.

## Configuration (`app/core/config.py`)
`APP_ENV` (`development` | `test` | `production`; anything else counts as production), `DATABASE_URL`, `PHI_KEK` (base64 of 32 bytes), `JWT_SECRET`, `CORS_ORIGINS` (comma-separated), `DEFAULT_TENANT_ID` (default `default`), `AUTO_MIGRATE`, `SEED_ON_STARTUP`, `LLM_PROVIDER` (`mock` | `anthropic` | `bedrock` | `none`; defaults to `mock` in development/test and `none` elsewhere), `ANTHROPIC_API_KEY`, `AWS_REGION` (Bedrock), `LLM_SUMMARY_MODEL` (default `claude-sonnet-5-5`), `LLM_ASSISTANT_MODEL` (default `claude-haiku-5-5`), `LOG_FORMAT` (`json` default in production, `text` in dev), `LOG_LEVEL`, `PHI_KEK_PREVIOUS` (comma-separated retired KEKs during rotation), `DB_HOST`/`DB_PORT`/`DB_NAME`/`DB_USER`/`DB_PASSWORD` (used to build the URL when `DATABASE_URL` is unset, as on ECS), `OTEL_EXPORTER_OTLP_ENDPOINT` (turns on tracing if `requirements-otel.txt` is installed), `ENABLE_DEV_LOGIN` (development/test only: enables `POST /api/auth/dev-login` for E2E; production settings force it off), `NOTIFICATION_STREAM_SECONDS` (how long one SSE notification stream stays open before the client reconnects; default 25, under the Vercel function limit), `ALLOWED_EMAIL_DOMAINS` (comma-separated; when set, only these domains may request an account), `SELF_REGISTRATION` (default `true`; `false` means invite-only).
- In production, a missing `DATABASE_URL` or `PHI_KEK` fails at settings load. A missing `JWT_SECRET` fails in `create_app()` only, so migrations and the CLI run without it.
- In dev these default to `backend/dischargeflow.db` (SQLite), a fixed development-only KEK, and an ephemeral JWT secret (sessions die on restart).
- `normalize_database_url` accepts provider URLs (`postgres://…?sslmode=require`) and converts them for asyncpg. `-pooler` hosts get PgBouncer-safe settings.
- `AUTO_MIGRATE=true` (set on Vercel) migrates on the first request per process, under a Postgres advisory lock (`core/migrate.py`). It exists because Vercel has no release step and every preview gets a fresh Neon branch. Elsewhere, run `app.cli migrate` as a one-off job.

## Backend architecture

`server.py` is only a shim (`from app.main import app`) so that uvicorn, the Dockerfile and `vercel.json` keep working. `app/main.py:create_app` wires the middleware and mounts each module's router under `/api`.

Modular monolith: each package in `app/` owns its tables (`models.py`) and HTTP surface (`router.py`), plus `service.py` where logic is shared. `app/models.py` imports every model so `Base.metadata` is complete for Alembic and tests; **a new model must be added there.** Modules: `identity` (users, Emergent OAuth session exchange), `patients` (incl. consent/erasure), `discharge` (workflows + tasks), `ai` (LLM gateway, prompts, de-identification, summaries, evals), `notifications`, `analytics`, `insurance`, `chatbot` (tool-calling assistant), `audit`, `interop` (read-only FHIR R4 at `/api/fhir/R4`, inbound HL7 v2 ADT at `/api/hl7/adt`).
- **Module boundaries (`backend/.importlinter`, checked by `lint-imports` in CI):** provider SDKs (`anthropic`, `boto3`) only in `app.ai.llm`; `app.core` imports no feature module except `identity` (plus the PHI backfill in `core/migrate.py`); `audit` and `notifications` are leaves; nothing imports `chatbot` or `interop`; only `app.main` imports a `router`. Shared helpers go in `service.py`, never in a router. The ADR's stricter "only through service.py" rule is not enforced yet (modules still read each other's models). `VERSION` lives in `core/config.py`.

Key conventions:
- **One transaction per request.** Routes take `db: DB` (`app/core/db.py`), a dependency declared with `scope="function"`, so it commits *before* the response is sent and rolls back everything on any exception. Services `flush()` instead of committing. Audit rows (`audit.service.write_audit`) and notifications go into the same transaction as the change they describe.
- **The discharge state machine lives in `discharge/service.py`.** `sync_workflow_status` moves a workflow `in_progress ⇄ pending_approval` based on open tasks; call it after any task change (task routes, summary approval and the chatbot all do). `complete_discharge` requires zero open tasks and an approved summary. The database enforces one active workflow per patient with a partial unique index (`uq_workflows_one_active_per_patient`) and one summary per workflow with a unique constraint.
- IDs are prefixed strings (`pat_…`, `wf_…`, `task_…`), kept from the Mongo era so the API contract didn't change. `Base.to_dict()` serializes rows with ISO datetimes, which is the shape the frontend expects. `UTCDateTime` keeps timestamps timezone-aware on SQLite as well. SQLite runs with `PRAGMA foreign_keys=ON`.
- Tasks may have `workflow_id = NULL` (ad-hoc tasks with no active discharge). `priority` is an int: 1 high, 2 medium, 3 low.
- **Task ownership (`discharge/service.update_task`):** only the assignee (the named `assigned_to` user or anyone in `assigned_role`) changes a task's status. Anyone else needs `task:override` (physician, admin) plus a `reason`, stored on the task (`override_reason`, `override_by`) and not in the audit entry. Setting `assigned_to` needs `task:assign`, except someone in the task's role claiming it. The assistant's `update_task_status` tool goes through the same function, so the same rule applies.
- `PatientUpdate` whitelists editable fields and silently ignores any others.
- **Auth:**
  - Access tokens are 15-minute HS256 JWTs (`sub`, `sid`, `tid`, `typ=access`), sent only as a Bearer header.
  - `get_current_user` loads the role from the database and checks the `auth_sessions` row is still active, cached 30 s per process. Role changes and logout therefore apply within seconds. Call `invalidate_identity()` after changing either.
  - The refresh token lives in the `df_refresh` cookie (httpOnly, SameSite=Strict, `Path=/api/auth`) as `tenant.session.secret`; only its SHA-256 is stored. It rotates on every `/api/auth/refresh`. Reuse of the previous token after a 30 s grace period revokes the session (`identity/sessions.py`).
  - Login: frontend → `auth.emergentagent.com` → `#session_id=` in the URL hash → `POST /api/auth/session`. Existing and invited users (`POST /api/users` pre-creates the row by email; the match ignores case) sign in with their role. An unknown account joins `DEFAULT_TENANT_ID` as `pending`, if `SELF_REGISTRATION` is on and its domain is in `ALLOWED_EMAIL_DOMAINS` (any domain when unset), and is refused with 403 otherwise. Admins are notified and approve by setting a role.
  - `pending` holds no permissions, and `get_current_user` (`AuthUser`) refuses it with 403 on every route. Many reads need no permission, so this check is what keeps a pending account away from patient data. Only `/api/auth/me` uses `SignedInIdentity`, which lets it through; the frontend then shows `pages/PendingApproval.jsx`. `pending` is not in `permissions.ROLES` (not a task role); `ASSIGNABLE_ROLES` is what an admin may set.
  - The frontend keeps the access token in memory only (`AuthContext.js`), refreshes on load and before expiry, and retries once on a 401. `AuthContext.login()` warns not to hard-code the redirect URL.
- **Permissions:** endpoints use `Depends(requires("<permission>"))`. The `role_permissions` table maps roles to permissions (seeded by migration 0002 from `identity/permissions.py:DEFAULT_ROLE_PERMISSIONS`; admin holds all). A new permission needs a migration that inserts its rows.
- **Tenancy:**
  - Every tenant-scoped model uses `TenantMixin` (`tenant_id` defaults from the `current_tenant_id` contextvar and raises if unset).
  - On Postgres, `use_tenant(db, tenant_id)` runs `SET LOCAL ROLE dischargeflow_app` and sets `app.tenant_id`. RLS policies (`core/rls.py`, frozen copy in migration 0002) then filter and check every row. Auth does this automatically.
  - Unauthenticated code paths (login, refresh, seed, CLI) must call `use_tenant` themselves.
  - A new tenant-scoped table needs `TenantMixin`, an entry in `rls.TENANT_TABLES`, and a migration adding its policy and grants. A test compares migrated policies with `TENANT_TABLES`.
  - SQLite has no RLS, so local SQLite is effectively single-tenant.
- **PHI:**
  - `Patient.name`, `date_of_birth` and `diagnosis` are synonyms over ciphertext columns: AES-256-GCM with a per-patient data key wrapped by `PHI_KEK`, with the patient id and field as associated data (`core/crypto.py`).
  - They can't be filtered or sorted in SQL; load and filter in Python, as the chatbot's patient lookup does.
  - `Patient.shred()` (erasure) destroys the key and overwrites the fields.
  - `DischargeSummary.content`, `original_content`, `edit_diff` and `structured` (ciphertext of its JSON) use the same scheme with the patient's data key (AAD: summary id + field); the `patient` relationship is always joined so the key is at hand. Set `patient` before the text when constructing one. Erasure also calls `DischargeSummary.shred()`, and a summary whose patient key is gone reads as `[REDACTED]` (`structured` as `None`). `app.cli migrate` backfills legacy plaintext summaries.
  - `Patient.mrn` (from HL7 PID-3) is encrypted the same way. `mrn_index` is a blind index: HMAC-SHA256 over (tenant, assigning authority, MRN) with a key HKDF-derived from `PHI_KEK` (`crypto.blind_index`), unique per tenant, the only way to find a patient by MRN. Set it with `Patient.set_mrn()`; look up with `crypto.blind_index_candidates` (also matches indexes made under `PHI_KEK_PREVIOUS`). `rewrap-deks` recomputes indexes, and erasure clears them.
  - Never log or return `phi_dek` or `mrn_index`. `__api_exclude__` keeps them out of `to_dict()`.
- **Audit:**
  - `audit.service.write_audit` locks the tenant's `audit_chain_heads` row and appends an entry whose SHA-256 covers its fields plus the previous hash. `GET /api/audit/verify` recomputes the chain.
  - `audit_logs` is append-only: triggers block UPDATE and DELETE for every role, and the app role only has INSERT and SELECT. Never write code that edits audit rows.
  - Every write to patients, workflows, tasks, claims, users and summaries is audited. Details never carry PHI or free text: field names instead of values, ids instead of names (audit rows survive erasure).
  - PHI reads are audited with `audit.service.audit_phi_read`: one `PHI_READ` entry per request (a list is one entry, not one per row), resource type `patient` with the patient id, so `GET /api/audit/patients/{id}` shows who read the record. The patient list, patient detail, workflow detail (both routes) and summary read do this; FHIR reads log `FHIR_READ`. A new route that returns patient-level data should call it. The entry joins the request's transaction, so a read that fails is not logged.
- **AI gateway (`ai/llm.py`):** every model call goes through `get_llm_client(purpose)` and the `LLMClient` interface. Adapters: `ClaudeClient` (Anthropic API or Bedrock, same SDK) and `MockLLMClient` (deterministic, offline; only restates facts it is given). Never import a provider SDK elsewhere. With `LLM_PROVIDER=none` summaries return 503; the assistant falls back to the mock. A refusal or provider error raises `LLMError` (no silent model fallback, so provenance names the real model).
- **Prompts (`ai/prompts/<name>@<version>.md`):** `ACTIVE` picks the version. Never edit a published version: add the next one, point `ACTIVE` at it and pin its hash in `tests/test_ai.py:PROMPT_HASHES`.
- **De-identification (`ai/deid.py`):** text sent to a model has names replaced by tokens (`[PATIENT_1]`), contact details and dates scrubbed, and only the fields the prompt needs (`ai/service.summary_facts`: age, length of stay, diagnosis, task titles, physician notes). Output is re-identified. Names shared by two people become `[AMBIGUOUS_NAME]`.
- **Summaries (`ai/service.py`):** structured JSON validated by `ai/schemas.DischargeSummaryDoc`, one retry on invalid output, then a visible 502. Grounding warnings (`ai/grounding.py`: meds/diagnoses not in the input) are stored with the draft. Every call adds an `ai_generations` provenance row (model, prompt version, input hash, tokens, latency; never prompt/output text). A failed generation returns a `JSONResponse` instead of raising so its provenance and audit rows still commit. Approval accepts the physician's edited `content` and stores `original_content`, `edit_diff` and `edit_similarity`.
- **Evals (`ai/evals/`):** `golden_set.json` holds synthetic patients with expected and forbidden facts; `python -m app.ai.evals` runs them through `run_summary_model` (the production path) and exits non-zero on any hallucination, PHI leak, failure, or coverage below the threshold. A prompt or model change must keep it green.
- **Integration clients and HL7 ADT (`identity/integrations.py`, `interop/adt.py`):**
  - Hospital systems authenticate with an API key (`X-API-Key: <tenant>.<client_id>.<secret>`, only the SHA-256 stored), created and revoked by admins at `/api/integrations/clients` (`user:manage`), shown once. A client acts as the role `interface` (`permissions.INTEGRATION_ROLE`, not in `ROLES`, so no person can be given it), which holds only `adt:ingest` (migration 0007). Endpoints for clients use `Depends(requires_integration("<permission>"))`; audit rows name the client id.
  - `POST /api/hl7/adt` takes one ER7 message (the interface engine bridges MLLP to HTTPS) and returns its ACK with HTTP 200: AA, AE (application refused: unknown MRN, already admitted, state machine) or AR (unsupported type, event or processing id; unparseable). A01 admits a new MRN or readmits a discharged one; A03 calls `discharge.service.complete_discharge`, and when that refuses, the ACK is AE with its reason and physicians are notified. `hl7_messages` stores each (client, MSH-10) with its ACK, never the message, so resends replay the ACK. ACK texts and audit details carry reasons and ids only.
- **Assistant (`chatbot/`):** an LLM tool-calling loop over `chatbot/tools.py`, which wraps the same service functions as the HTTP API (`discharge.service.create_task`/`update_task`/`initiate_discharge`, `insurance.service.create_claim`). Each tool declares the permission its endpoint requires (checked with `security.ensure_permission`) and every call is audited. Write tools never run from the model: they create an `assistant_actions` proposal that the same user confirms (`POST /api/chatbot/actions/{id}/confirm`, single use, 10-minute expiry, permission re-checked). Tool results are de-identified and wrapped in `<tool_data>` as untrusted data. A new tool needs an args model, its HTTP permission, and a test.

- **Notification stream (`notifications/stream.py`):** `GET /api/notifications/stream` is Server-Sent Events, authenticated with the normal Bearer header. There is no broker (and Neon's pooler can't LISTEN), so it polls the table every 5 s with its own short sessions from `get_session_factory()` (the request transaction has already committed when the body streams), re-checks the auth session each poll, and ends after `NOTIFICATION_STREAM_SECONDS`. Events carry only `notification_id`; clients refetch the list.
- **Operational metrics (`analytics/service.operational_metrics`, `GET /api/analytics/operations?days=`, `insights:read`):** throughput, time in `pending_approval`, task SLA breaches (targets in `TASK_SLA_HOURS`, policy defaults). Same no-PHI and small-group rules as `discharge_aggregates`. Change workflow status only through `discharge.service.set_workflow_status`, which accumulates `pending_approval_seconds`; NULL there means "not tracked" (workflows from before migration 0006), never zero.
- **Logging (`core/observability.py`):** never log patient fields, request bodies, prompts or model output. Log lines are JSON in production with `request_id`, `tenant_id` and `user_id` attached automatically, and a PHI scrubber redacts emails, phones, SSNs, MRNs and dates as a backstop. Pass structured fields with `extra={...}`.

## Frontend architecture
- Vite (`vite.config.js`); JSX lives in `.jsx` files. `package.json` is `"type": "module"`, so Tailwind/PostCSS configs are `.cjs`.
- **Routing (`App.jsx`):** one URL per screen, each lazy-loaded: `/dashboard`, `/patients`, `/patients/:patientId`, `/workflows/:workflowId`, `/tasks`, `/insurance`, `/assistant`, `/analytics`, `/insights` (admin), `/admin` (admin), all inside `pages/AppLayout.jsx` (sidebar + header + `<Outlet>`). `RoleRoute` keeps people off screens their role can't use; the API still enforces permissions. Notification links (`/patients/:id`, `/workflows/:id`) are real routes. If the URL hash contains `session_id=`, `AuthCallback` renders before routing runs. A new screen is a route in `App.jsx` plus a `NavLink` in `Sidebar.jsx`.
- **HTTP (`lib/api.js`):** the only client. `api.get('/patients')` adds the base URL, credentials, the in-memory bearer token, and refresh-and-retry on 401. Never import axios directly or build URLs from env vars in components. `errorMessage(error)` reads FastAPI's `detail`.
- **Server state (`lib/queries.js`):** TanStack Query hooks (`usePatients`, `useWorkflow(id)`, ...) with hierarchical `keys`. Views read through hooks instead of fetching into `useState`. After a mutation, `await` an invalidation (`invalidateDischarge()` for anything that moves workflows, tasks, patients or notifications) before clearing loading state, so controls don't flicker back to stale values.
- **Live notifications (`lib/notificationStream.js`):** `useNotificationStream()` (mounted in `AppLayout`) reads the SSE stream with `fetch` so the token stays in a header, invalidates `keys.notifications` on each event, reconnects when the server ends a stream and backs off on errors. `useNotifications` polls every 30 s only while the stream is not live.
- Tests: Vitest + Testing Library (`src/**/*.test.jsx`, mock `api` with `vi.spyOn`), Playwright in `e2e/` (sign in with `signInAs(page, role)`, which uses the dev login).
- UI: shadcn/ui (Radix) components in `components/ui/`, Tailwind, a forced dark theme, lucide icons and Recharts. The `@/` alias points to `src/`. Design tokens are in `design_guidelines.json`.

## Deployment notes
- AWS (not yet applied): `infra/` (see `infra/README.md`), `.github/workflows/deploy.yml` (dormant until the `AWS_DEPLOY_ENABLED` repository variable is `true`), `scripts/deploy/ecs_deploy.sh`, `scripts/smoke_test.py`, and runbooks in `docs/runbooks/`. Migrations must stay compatible with the previous release, because the deploy migrates before rolling out.
- `vercel.json` serves `backend/server.py` as a Python function. `server.py` puts `backend/` on `sys.path` because Vercel imports it by path from the repo root.
- Production runs on Neon Postgres via the Vercel integration, which injects `DATABASE_URL`. Preview deployments get their own Neon branch.
- Vercel env: `APP_ENV=production`, `JWT_SECRET`, `PHI_KEK`, `CORS_ORIGINS`, `AUTO_MIGRATE=true`. On Vercel, `make_engine` uses `NullPool`.
- `k8s/` has a Postgres StatefulSet, a `backend-migrate` Job, and a backend Deployment that reads a `backend-secrets` Secret (see the comments in each file).

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

DischargeFlow is a hospital discharge management system: a FastAPI backend (`backend/app/`) on SQLAlchemy + PostgreSQL, and a Vite + React 19 frontend (`frontend/`). It was scaffolded on the Emergent platform (`.emergent/`, Emergent Auth). Product requirements are in `memory/PRD.md`, the user-facing overview is `README.md`, and every endpoint with the permission it requires is in `docs/api.md` (update it when adding or changing a route). **The target architecture and Phases 1–6 are in `docs/architecture/ADR-001-production-architecture.md`; ADR-002 (`docs/architecture/ADR-002-hospital-readiness.md`) validates it against real-hospital use and plans Phases 7–9.** Phase 1 (modular backend + Postgres + Alembic + tests) and Phase 2 (hardened sessions, DB-backed permissions, tenant RLS, PHI encryption, tamper-evident audit) are done. Phase 2 kept the Emergent Google login rather than switching to Cognito. Phase 3 (governed AI layer: LLM gateway, de-identification, structured summaries with provenance, golden-set evals, tool-calling assistant) is done except the async outbox/SQS worker (item 11). Phase 4 (Terraform for AWS, deploy pipeline, observability, runbooks) is written and validated but not applied: there is no AWS account, so production still runs on Vercel + Neon. Phase 5 (Vite + TanStack Query + URL routes, Playwright E2E, read-only FHIR R4, admin AI insights) is done. Phase 6 (live notification stream over SSE, operational metrics, import-linter/mypy/Dependabot gates, inbound HL7 v2 ADT) is done. In ADR-002's Phase 7 (pilot readiness), the items that need no AWS account are done: 1 (approval-gated sign-up, task ownership, claim permissions, write and PHI-read audit coverage), 3 (unit-scoped access with break-glass), 4 (idle lock) and 6 (downtime procedure: read-only mode, printable discharge census, backfill of paper work). Items 2 (hospital SSO) and 5 (AWS under a BAA) are deferred until there is an AWS account; their code seams (OIDC ID-token sign-in, KMS key provider) are built. In Phase 8, items 7 (Patient/Encounter split), 8-10 (discharge plan reviewed daily, workflow templates per disposition with prerequisites and due times, delay reason codes; migration 0014), 11 (ADT reconciliation: A03 → `externally_discharged`, A02/A08/A11/A13/A40, parked out-of-order messages), 12 (escalation of overdue tasks, migration 0012) and 13 (discharge summary lifecycle: signed versions, addenda, sign-by deadline, migration 0013) are done. In Phase 9, item 21 (notification delivery over Postgres LISTEN/NOTIFY on long-running hosts, migration 0016) is done; production on Vercel still polls until the AWS move. Item 18 (patient-facing discharge instructions in plain language and the patient's language, clinician-approved; migration 0017) is done. Items 14 (SMART on FHIR EHR launch) and 15 (read-only clinical context from the EHR: medications, problems, allergies) are done too (migration 0018), tested against a fake EHR only. Items 17 (capacity board and bed turnover, migration 0019) and 19 (outcome analytics) are done.

`project_implementation_plan.md` predates the repo audit (it assumes Node and microservices) and is superseded by ADR-001. `project_overview.md` describes a different project (SkillGraph V2). `test_result.md`, `test_reports/` and `branches.txt` are leftovers from the Emergent platform. Ignore all of them.

## Commands

Backend (run from `backend/`, with `venv` active):
```bash
pip install -r requirements.txt
python -m app.cli migrate            # alembic upgrade head + encrypt any plaintext PHI (use this, not bare alembic)
python -m app.cli seed               # idempotent demo patients; refuses in production without --force
python -m uvicorn server:app --port 8000 --reload
python -m pytest                     # full suite, in-memory SQLite
ruff check .                         # lint gate in CI (errors only, see ruff.toml)
lint-imports                         # module-boundary contracts in .importlinter (CI gate)
mypy                                 # type check of the modules listed in mypy.ini (CI gate; app.ai and app.chatbot not yet)
python -m app.cli rewrap-deks        # PHI KEK rotation step, see docs/runbooks/rotate-secrets.md
python -m app.cli summary-deadlines  # notify physicians of summaries unsigned past SUMMARY_SIGN_HOURS (schedule it; idempotent)
python -m app.cli escalate           # escalate overdue tasks in every tenant (idempotent; what Vercel Cron runs)
python -m app.ai.evals               # golden-set AI evals on the mock adapter (CI gate); --provider anthropic --model claude-haiku-5-5 for a real model
python -m pytest tests/test_discharge_workflow.py::test_full_discharge_happy_path   # single test
alembic revision --autogenerate -m "describe change"   # after editing models; review the generated file
```
Run the suite against Postgres by setting `TEST_DATABASE_URL=postgresql+asyncpg://...`. CI runs both SQLite and a Postgres 16 service. Tenant-isolation (RLS) tests are marked `requires_postgres` and only run against Postgres. `tests/test_platform.py` shells out to Alembic to check `upgrade` → `check` (model/migration drift) → `downgrade`, and upgrades real 0001-era data through `app.cli migrate`. A model change without a migration therefore fails the tests.

Frontend (from `frontend/`, Node 22):
```bash
npm ci
npm run dev                          # Vite on :3000, proxies /api to http://localhost:8000 (override with VITE_DEV_API)
npm run build                        # to frontend/build (the directory Vercel, the Dockerfile and deploy.yml expect)
npm test                             # Vitest + Testing Library
npx eslint .                         # lint gate in CI
npx playwright test                  # E2E: starts the backend (mock AI, dev login) and `vite preview` itself
```
For E2E locally, set `E2E_PYTHON` to the backend venv's python (absolute path on Windows), and `PW_CHANNEL=chrome` to use an installed Chrome instead of downloading Playwright's Chromium. `E2E_DATABASE_URL` picks the database (default: a throwaway SQLite file). `VITE_BACKEND_URL` (or the legacy `REACT_APP_BACKEND_URL`) points the built app at another API origin; empty means same-origin `/api`.

Full stack: `docker compose up --build` starts Postgres, runs a one-shot `migrate` service, then the backend (with `SEED_ON_STARTUP=true`) and the frontend.

see Patient instructions).
- In production, a missing `DATABASE_URL` or `PHI_KEK` fails at settings load. A missing `JWT_SECRET` fails in `create_app()` only, so migrations and the CLI run without it.
- In dev these default to `backend/dischargeflow.db` (SQLite), a fixed development-only KEK, and an ephemeral JWT secret (sessions die on restart).
- `normalize_database_url` accepts provider URLs (`postgres://…?sslmode=require`) and converts them for asyncpg. `-pooler` hosts get PgBouncer-safe settings.
- `AUTO_MIGRATE=true` (set on Vercel) migrates on the first request per process, under a Postgres advisory lock (`core/migrate.py`). It exists because Vercel has no release step and every preview gets a fresh Neon branch. Elsewhere, run `app.cli migrate` as a one-off job.

## Backend architecture

`server.py` is only a shim (`from app.main import app`) so that uvicorn, the Dockerfile and `vercel.json` keep working. `app/main.py:create_app` wires the middleware and mounts each module's router under `/api`.

Modular monolith: each package in `app/` owns its tables (`models.py`) and HTTP surface (`router.py`), plus `service.py` where logic is shared. `app/models.py` imports every model so `Base.metadata` is complete for Alembic and tests; **a new model must be added there.** Modules: `identity` (users, sign-in shared by every login method in `identity/service.py`, Emergent OAuth session exchange), `patients` (incl. encounters, consent/erasure), `discharge` (workflows + tasks), `ai` (LLM gateway, prompts, de-identification, summaries and their signed versions and addenda, patient instructions, evals), `notifications`, `analytics`, `insurance`, `chatbot` (tool-calling assistant), `audit`, `interop` (read-only FHIR R4 at `/api/fhir/R4`, inbound HL7 v2 ADT at `/api/hl7/adt`, SMART on FHIR EHR launch and the outbound FHIR client at `/api/smart`), `downtime` (read-only mode, discharge census, backfill windows), `escalations` (overdue-task escalation and paging), `capacity` (capacity board, bed turnover).
- **Module boundaries (`backend/.importlinter`, checked by `lint-imports` in CI):** provider SDKs (`anthropic`, `boto3`) only in `app.ai.llm`; `app.core` imports no feature module except `identity` (plus the PHI backfill in `core/migrate.py`); `audit` and `notifications` are leaves; nothing imports `chatbot` or `interop`; only `app.main` imports a `router`. Shared helpers go in `service.py`, never in a router. The ADR's stricter "only through service.py" rule is not enforced yet (modules still read each other's models). `VERSION` lives in `core/config.py`.

Key conventions:
- **One transaction per request.** Routes take `db: DB` (`app/core/db.py`), a dependency declared with `scope="function"`, so it commits *before* the response is sent and rolls back everything on any exception. Services `flush()` instead of committing. Audit rows (`audit.service.write_audit`) and notifications go into the same transaction as the change they describe.
- **The discharge state machine lives in `discharge/service.py`.** `sync_workflow_status` moves a workflow `in_progress ⇄ pending_approval` based on open tasks; call it after any task change (task routes, summary approval and the chatbot all do). `complete_discharge` requires zero open tasks and an approved summary. The database enforces one active workflow per patient and per encounter with partial unique indexes (`uq_workflows_one_active_per_patient`, `uq_workflows_one_active_per_encounter`) and one summary per workflow with a unique constraint. `complete_discharge` closes the workflow's encounter. When an HL7 A03 arrives first, `record_external_discharge` sets the status `externally_discharged` (not an active status, so the patient can be readmitted meanwhile): the encounter closes at `departed_at`, the patient is discharged, open tasks stay open until `documentation_due_at`, and `complete_discharge` later only closes the workflow (at `departed_at`, without touching the patient or encounter). `reopen_external_discharge` (A13) puts it back to `in_progress`.
- **Encounters (ADR-002 item 7):** `patients` → `encounters` (one stay: visit number, admit/discharge times, unit, room, disposition, `expected_discharge_date`, status `active` | `discharged`) → `workflows.encounter_id`. One active encounter per patient (`uq_encounters_one_active_per_patient`); a patient who is not discharged has exactly one. Open and close them through `patients/service.py` (`open_encounter`, `ensure_current_encounter`, `sync_encounter`): creating a patient and every A01 open one, a readmission is a new one, and manual status edits keep the invariant. The patient's `admission_date`, `room_number`, `unit_id` and `status` mirror the current encounter (the previous release and unit-scope RLS read them). `workflows.encounter_id` is nullable only for rows the previous release wrote during the rollout; `discharge.service.encounter_for` links them.
- IDs are prefixed strings (`pat_…`, `wf_…`, `task_…`), kept from the Mongo era so the API contract didn't change. `Base.to_dict()` serializes rows with ISO datetimes, which is the shape the frontend expects. `UTCDateTime` keeps timestamps timezone-aware on SQLite as well. SQLite runs with `PRAGMA foreign_keys=ON`.
- Tasks may have `workflow_id = NULL` (ad-hoc tasks with no active discharge). `priority` is an int: 1 high, 2 medium, 3 low.
- **Task ownership (`discharge/service.update_task`):** only the assignee (the named `assigned_to` user or anyone in `assigned_role`) changes a task's status. Anyone else needs `task:override` (physician, admin) plus a `reason`, stored on the task (`override_reason`, `override_by`) and not in the audit entry. Setting `assigned_to` needs `task:assign`, except someone in the task's role claiming it. The assistant's `update_task_status` tool goes through the same function, so the same rule applies.
- **Discharge plans, templates and delays (ADR-002 items 8-10; `discharge/planning.py`, `discharge/templates.py`):**
  - The plan is on the encounter (`expected_discharge_date`, `planned_disposition`, `plan_reviewed_at`/`_by`), changed only through `planning.update_plan` / `review_plan` (`plan:manage`); changing it counts as the day's review.
  - `initiate_discharge` takes its tasks from the active `workflow_templates` row for the planned disposition (one per disposition per tenant), else `STANDARD_TASKS`. Template tasks carry `due_at`, `due_offset_hours` (hours from 00:00 on the expected date, hospital time) and `depends_on` (task ids). Moving the date moves the open tasks' due times.
  - `update_task` refuses to start or complete a task with an open prerequisite (409, no override), and needs a delay code to complete a task past `models.due_time(...)` (template due time, else `TASK_SLA_HOURS` after creation) unless one is on record. A date moved later, or a passed date at the day's first review, needs one too. Delay notes are free text: never audited, redacted on erasure.
  - `DEFAULT_TEMPLATES` has a frozen copy in migration 0014; a test checks they agree. Change defaults with a new migration plus the app copy, never one alone. Every default template keeps a task titled `SUMMARY_TITLE` (approving the summary completes it).
- `PatientUpdate` whitelists editable fields and silently ignores any others.
- **Auth:**
  - Access tokens are 15-minute HS256 JWTs (`sub`, `sid`, `tid`, `typ=access`), sent only as a Bearer header.
  - `get_current_user` loads the role from the database and checks the `auth_sessions` row is still active, cached 30 s per process. Role changes and logout therefore apply within seconds. Call `invalidate_identity()` after changing either.
  - The refresh token lives in the `df_refresh` cookie (httpOnly, SameSite=Strict, `Path=/api/auth`) as `tenant.session.secret`; only its SHA-256 is stored. It rotates on every `/api/auth/refresh`. Reuse of the previous token after a 30 s grace period revokes the session (`identity/sessions.py`).
  - Login: frontend → `auth.emergentagent.com` → `#session_id=` in the URL hash → `POST /api/auth/session`. Existing and invited users (`POST /api/users` pre-creates the row by email; the match ignores case) sign in with their role. An unknown account joins `DEFAULT_TENANT_ID` as `pending`, if `SELF_REGISTRATION` is on and its domain is in `ALLOWED_EMAIL_DOMAINS` (any domain when unset), and is refused with 403 otherwise. Admins are notified and approve by setting a role.
  - Hospital SSO seam (ADR-002 item 2, not yet run against a real provider): with `OIDC_ISSUER` and `OIDC_CLIENT_ID` set, `POST /api/auth/oidc` verifies an ID token against the provider's JWKS (`identity/oidc.py`) and then signs in through the same `_sign_in` as the Google login, so the same matching and approval rules apply. The frontend does not use it yet.
  - `pending` holds no permissions, and `get_current_user` (`AuthUser`) refuses it with 403 on every route. Many reads need no permission, so this check is what keeps a pending account away from patient data. Only `/api/auth/me` uses `SignedInIdentity`, which lets it through; the frontend then shows `pages/PendingApproval.jsx`. `pending` is not in `permissions.ROLES` (not a task role); `ASSIGNABLE_ROLES` is what an admin may set.
  - The frontend keeps the access token in memory only (`AuthContext.jsx`), refreshes on load and before expiry, and retries once on a 401. `AuthContext.login()` warns not to hard-code the redirect URL.
  - **Idle lock (shared workstations, ADR-002 item 4):** after `IDLE_LOCK_MINUTES` with no input in any tab (`lib/idle.js`, last activity shared through localStorage), `AuthContext.lock()` blocks every non-auth request (`api.setClientLocked`), clears the access token, the TanStack Query cache and toasts, renders `LockScreen` instead of the app, tells other tabs to lock, and revokes the refresh session (`POST /auth/logout` with `{"reason": "idle"}`). Re-entry is a fresh sign-in; `login()` saves the path and `AuthCallback` returns to it. Resuming the old session without re-authenticating is deliberately not offered: the next person at the workstation could do it. A page loaded after the idle limit locks instead of resuming. As a backstop for tabs closed before they locked, `sessions.rotate` revokes a session not refreshed for `SESSION_IDLE_MINUTES` (`revoked_reason="idle_timeout"`); it must stay above the ~14-minute refresh interval of an open tab.
- **Permissions:** endpoints use `Depends(requires("<permission>"))`. The `role_permissions` table maps roles to permissions (seeded by migration 0002 from `identity/permissions.py:DEFAULT_ROLE_PERMISSIONS`; admin holds all). A new permission needs a migration that inserts its rows.
- **Tenancy:**
  - Every tenant-scoped model uses `TenantMixin` (`tenant_id` defaults from the `current_tenant_id` contextvar and raises if unset).
  - On Postgres, `use_tenant(db, tenant_id)` runs `SET LOCAL ROLE dischargeflow_app` and sets `app.tenant_id`. RLS policies (`core/rls.py`, frozen copy in migration 0002) then filter and check every row. Auth does this automatically.
  - Unauthenticated code paths (login, refresh, seed, CLI) must call `use_tenant` themselves.
  - A new tenant-scoped table needs `TenantMixin`, an entry in `rls.TENANT_TABLES`, and a migration adding its policy and grants. A test compares migrated policies with `TENANT_TABLES`.
  - SQLite has no RLS, so local SQLite is effectively single-tenant.
  - **Unit scope (ADR-002 item 3):** with `UNIT_SCOPED_ACCESS` on, users whose role lacks `patient:read_all` (admin and `interface` hold it) are scoped: `get_signed_in_identity` calls `tenancy.use_access_scope`, which sets `app.unit_scope='on'`, `app.user_id` and `app.unit_ids`. The RESTRICTIVE `unit_scope` policies (`rls.UNIT_SCOPED_TABLES`: patients, workflows, tasks, discharge_summaries, insurance_claims, discharge_summary_versions, discharge_summary_addenda) then show a patient only if it is on one of the user's units, has no unit, or has an unexpired `access_grants` row for the user (break-glass). Child tables check `EXISTS (patient)`, which runs under the patients policies. Without the setting the policy is inactive, so login, the CLI, migrations and the ADT feed see the whole tenant. A new table holding patient data needs an entry in `UNIT_SCOPED_TABLES` and a migration adding its policy (a test compares them). `df_patient_exists()` (SECURITY DEFINER) tells "hidden" (403 with `break_glass: true`) from "missing" (404). Notifications about a patient pass `unit_id` to `notify_role`, so only that unit's staff are told. `CurrentUser.unit_ids`/`unit_scoped` are cached with the identity, so call `invalidate_identity` after changing memberships. SQLite does not enforce unit scope; its tests are `requires_postgres` (`tests/test_unit_scope.py`).
- **PHI:**
  - `Patient.name`, `date_of_birth` and `diagnosis` are synonyms over ciphertext columns: AES-256-GCM with a per-patient data key wrapped by `PHI_KEK`, with the patient id and field as associated data (`core/crypto.py`).
  - They can't be filtered or sorted in SQL; load and filter in Python, as the chatbot's patient lookup does.
  - `Patient.shred()` (erasure) destroys the key and overwrites the fields.
  - `DischargeSummary.content`, `original_content`, `edit_diff` and `structured` (ciphertext of its JSON), and the `content` of its signed versions and addenda, use the same scheme with the patient's data key (AAD: summary id + field); the `patient` relationship is always joined so the key is at hand. Set `patient` before the text when constructing one. Erasure also calls `DischargeSummary.shred()`, and a summary whose patient key is gone reads as `[REDACTED]` (`structured` as `None`). `app.cli migrate` backfills legacy plaintext summaries.
  - `Patient.mrn` (from HL7 PID-3) is encrypted the same way. `mrn_index` is a blind index: HMAC-SHA256 over (tenant, assigning authority, MRN) with a key HKDF-derived from `PHI_KEK` (`crypto.blind_index`), unique per tenant, the only way to find a patient by MRN. Set it with `Patient.set_mrn()`; look up with `crypto.blind_index_candidates` (also matches indexes made under `PHI_KEK_PREVIOUS`). `rewrap-deks` recomputes indexes, and erasure clears them.
  - `PHI_KEY_PROVIDER=kms` (ADR-002 item 5, not yet run against AWS) wraps new data keys with `core/kms.KmsKeyProvider`; `PHI_KEK` then only unwraps older keys (until `rewrap-deks`) and derives the blind-index key. `app.core.kms` is the only `app.core` module allowed to import boto3.
  - `Encounter.visit_number` (PV1-19) is encrypted with the patient's data key (AAD: encounter id); the `patient` relationship is always joined. It can't be queried in SQL; compare after decrypting (few rows per patient). Erasure overwrites it.
  - Never log or return `phi_dek` or `mrn_index`. `__api_exclude__` keeps them out of `to_dict()`.
- **Audit:**
  - `audit.service.write_audit` locks the tenant's `audit_chain_heads` row and appends an entry whose SHA-256 covers its fields plus the previous hash. `GET /api/audit/verify` recomputes the chain.
  - `audit_logs` is append-only: triggers block UPDATE and DELETE for every role, and the app role only has INSERT and SELECT. Never write code that edits audit rows.
  - Every write to patients, workflows, tasks, claims, users and summaries is audited. Details never carry PHI or free text: field names instead of values, ids instead of names (audit rows survive erasure).
  - PHI reads are audited with `audit.service.audit_phi_read`: one `PHI_READ` entry per request (a list is one entry, not one per row), resource type `patient` with the patient id, so `GET /api/audit/patients/{id}` shows who read the record. The patient list, patient detail, workflow detail (both routes) and summary read do this; FHIR reads log `FHIR_READ`. A new route that returns patient-level data should call it. The entry joins the request's transaction, so a read that fails is not logged.
- **AI gateway (`ai/llm.py`):** every model call goes through `get_llm_client(purpose)` and the `LLMClient` interface. Adapters: `ClaudeClient` (Anthropic API or Bedrock, same SDK) and `MockLLMClient` (deterministic, offline; only restates facts it is given). Never import a provider SDK elsewhere. With `LLM_PROVIDER=none` summaries return 503; the assistant falls back to the mock. A refusal or provider error raises `LLMError` (no silent model fallback, so provenance names the real model).
- **Prompts (`ai/prompts/<name>@<version>.md`):** `ACTIVE` picks the version. Never edit a published version: add the next one, point `ACTIVE` at it and pin its hash in `tests/test_ai.py:PROMPT_HASHES`.
- **De-identification (`ai/deid.py`):** text sent to a model has names replaced by tokens (`[PATIENT_1]`), contact details and dates scrubbed, and only the fields the prompt needs (`ai/service.summary_facts`: age, length of stay, diagnosis, task titles, physician notes). Output is re-identified. Names shared by two people become `[AMBIGUOUS_NAME]`.
- **Summaries (`ai/service.py`):** structured JSON validated by `ai/schemas.DischargeSummaryDoc`, one retry on invalid output, then a visible 502. Grounding warnings (`ai/grounding.py`: meds/diagnoses not in the input) are stored with the draft. Every call adds an `ai_generations` provenance row (model, prompt version, input hash, tokens, latency; never prompt/output text). A failed generation returns a `JSONResponse` instead of raising so its provenance and audit rows still commit. Approval accepts the physician's edited `content` and stores `original_content`, `edit_diff` and `edit_similarity`.
- **Summary lifecycle (`ai/lifecycle.py`, ADR-002 item 13):**
  - Approval is the signature: `lifecycle.sign` stores the text as `DischargeSummaryVersion` 1 (`signed_by`, `signed_at`, `content_sha256`). After that the summary's `content` is frozen: setting different text raises `SignedSummaryError`. Never add a route that edits signed text; changes after signature are addenda.
  - `DischargeSummaryAddendum` (`POST /api/ai/summaries/{id}/addenda`) belongs to the latest signed version and is signed by its author as it is added; never edited or removed. `lifecycle.summary_view` is the read shape (signed version with `hash_verified`, version history, addenda, `sign_by`); FHIR `DocumentReference` sends the signed version plus one attachment per addendum (`docStatus` `amended`).
  - Versions and addenda are encrypted like the summary (`ai/models._PatientKeyedText`, AAD: their own id + field), loaded with it (`selectin`), and shredded by `DischargeSummary.shred()`. Audit details name version and addendum ids only. `app.cli migrate` gives summaries signed before migration 0013 their version 1.
  - Sign-by deadline (`lifecycle.sign_by`): `SUMMARY_SIGN_HOURS` after `completed_at`, or after the expected discharge time (then `started_at`) while the patient is still here. Overdue summaries appear in `operational_metrics` (`summary_signing`), `GET /api/ai/summaries/overdue`, and the workflow detail (`summary_overdue`). `lifecycle.notify_overdue` (CLI `summary-deadlines`, or `POST /api/ai/summaries/overdue/notify`) notifies the unit's physicians once per discharge; nothing schedules it yet.
- **Patient instructions (`ai/instructions.py`, ADR-002 item 18):**
  - Drafted only from the **signed** summary: its latest signed version plus that version's addenda (`instructions.signed_source`), never the draft or the structured JSON. Same governed path as summaries: `instruction_facts` de-identifies, prompt `patient_instructions@v1`, JSON validated by `schemas.PatientInstructionsDoc` (headings in the patient's language; what happened, conditions, medicines, warning signs, follow-up, activity and diet), `run_instructions_model` (what the evals run), an `ai_generations` row with purpose `patient_instructions`, 502 `JSONResponse` on failure.
  - One retry, for invalid output **or** for English text above `PATIENT_INSTRUCTIONS_TARGET_GRADE`; a draft still above it is kept with a `readability` warning. `ai/readability.py` is a deterministic Flesch-Kincaid grade, English only: other languages get `None`, never a number.
  - `grounding.check_instructions_grounding`: every medicine name and condition `medical_term` must appear in the signed text (the prompt has the model copy them untranslated, which is what makes the check work across languages), lexicon drugs mentioned anywhere too, and a discharge medication in the summary missing from the instructions is an `omission`.
  - `PatientInstructions` (`patient_instructions`, one per workflow and language): `content`, `original_content`, `edit_diff`, `structured` encrypted with the patient's data key like summaries (`_PatientKeyedText`), shredded on erasure, re-keyed on A40 merge, tenant- and unit-scoped. `source_sha256` hashes the signed source, so a later addendum shows as `stale`. An unapproved draft in the same language is replaced by a new one; approved text is frozen (`SignedSummaryError`).
  - Approval (`instructions:manage`, physician and nurse) stores the edit diff like summaries; only approved instructions print (`GET .../print`, PHI-read audited; frontend `/instructions/:id/print`).
  - `patients.preferred_language` is a BCP 47 code (`LANGUAGE_TAG_PATTERN`), not encrypted (a language is not an identifier on its own). The mock adapter writes English whatever language is asked: translation is only as good as the real model, and nothing in CI checks it.
- **Evals (`ai/evals/`):** `golden_set.json` holds synthetic patients with expected and forbidden facts (and, under `patient_instructions`, synthetic signed summaries with the readability gate); `python -m app.ai.evals` runs them through `run_summary_model` (the production path) and exits non-zero on any hallucination, PHI leak, failure, or coverage below the threshold. A prompt or model change must keep it green.
- **Integration clients and HL7 ADT (`identity/integrations.py`, `interop/adt.py`):**
  - Hospital systems authenticate with an API key (`X-API-Key: <tenant>.<client_id>.<secret>`, only the SHA-256 stored), created and revoked by admins at `/api/integrations/clients` (`user:manage`), shown once. A client acts as the role `interface` (`permissions.INTEGRATION_ROLE`, not in `ROLES`, so no person can be given it), which holds only `adt:ingest` (migration 0007). Endpoints for clients use `Depends(requires_integration("<permission>"))`; audit rows name the client id.
  - `POST /api/hl7/adt` takes one ER7 message (the interface engine bridges MLLP to HTTPS) and returns its ACK with HTTP 200: AA, AE (application refused: already admitted, wrong visit, state the event can't apply to) or AR (unsupported type, event or processing id; unparseable). `adt.HANDLERS` maps each event: A01 admits a new MRN or readmits a discharged one, each opening an encounter (an A01 whose PV1-19 visit was already seen, cancelled ones aside, is AE); A02 moves unit and room on the patient and encounter; A03 calls `discharge.service.complete_discharge`, and when that refuses, `record_external_discharge` (AA, never AE: the patient has left); A08 updates `UPDATABLE_FIELDS` only; A11 marks the encounter `cancelled` (AE if a workflow exists); A13 reopens the last stay; A40 calls `patients/merge.merge_into`, which moves encounters, workflows, tasks, summaries, claims and grants to the survivor and **re-encrypts** visit numbers and summary texts with the survivor's data key, then sets `merged_into` and clears the old `mrn_index` (merged records are left out of the patient list). Any event but A01/A40 must name a PV1-19 visit that matches, if it gives one. `hl7_messages` stores each (client, MSH-10) with its ACK, never the message, so resends replay the ACK. ACK texts and audit details carry reasons and ids only.
  - **Parking (`interop/parking.py`, `hl7_parked_messages`):** an event for an MRN with no patient (an A03 before its A01) is answered AA "Parked: …" and stored as ciphertext under its own wrapped data key (AAD: parked id), keyed by the MRN's blind index. `adt.receive` replays parked messages for an MRN after the A01 (or A40 re-key) that brings it in, in arrival order and in the same transaction, and expires overdue ones first (admins notified). Once replayed, expired or discarded, the ciphertext and key are dropped. Admins list them at `GET /api/hl7/parked` (`user:manage`). Never return or log `message`, `dek` or `mrn_index` (`__api_exclude__`).
- **Assistant (`chatbot/`):** an LLM tool-calling loop over `chatbot/tools.py`, which wraps the same service functions as the HTTP API (`discharge.service.create_task`/`update_task`/`initiate_discharge`, `insurance.service.create_claim`). Each tool declares the permission its endpoint requires (checked with `security.ensure_permission`) and every call is audited. Write tools never run from the model: they create an `assistant_actions` proposal that the same user confirms (`POST /api/chatbot/actions/{id}/confirm`, single use, 10-minute expiry, permission re-checked). Tool results are de-identified and wrapped in `<tool_data>` as untrusted data. A new tool needs an args model, its HTTP permission, and a test.

- **Notification stream (`notifications/stream.py`, `notifications/hub.py`, ADR-002 item 21):** `GET /api/notifications/stream` is Server-Sent Events, authenticated with the normal Bearer header, ending after `NOTIFICATION_STREAM_SECONDS`. Events carry only `notification_id`; clients refetch the list (also on a mid-stream `ready`). Two transports (`NOTIFICATION_TRANSPORT`):
  - `poll` (default; what Vercel runs, since a function can't hold a LISTEN and Neon's pooler drops one): polls the table every 5 s with its own short sessions from `get_session_factory()` (the request transaction has already committed when the body streams) and re-checks the auth session each poll.
  - `listen` (long-running hosts: ECS, docker-compose and k8s set it): the AFTER INSERT trigger `notifications_notify` (migration 0016; app copy `rls.NOTIFY_TRIGGER_PG`, installed by the test fixture) sends `pg_notify('notifications', 'tenant:user:id')`, delivered only on commit. `hub.get_hub()` keeps one asyncpg connection per process with `LISTEN` on `DATABASE_DIRECT_URL` or `db.direct_connection_dsn(DATABASE_URL)` (strips Neon's `-pooler`; other pooled URLs need the setting), reconnects with backoff and sends every subscriber a resync (`None` → another `ready`) after a reconnect. Streams re-check the auth session every 15 s. No hub (SQLite, pooled URL) or a hub not connected within 3 s means that stream polls. Never put notification text in the payload.
- **Operational metrics (`analytics/service.operational_metrics`, `GET /api/analytics/operations?days=`, `insights:read`):** throughput, time in `pending_approval`, task SLA breaches (targets in `TASK_SLA_HOURS`, policy defaults). Same no-PHI and small-group rules as `discharge_aggregates`. Change workflow status only through `discharge.service.set_workflow_status`, which accumulates `pending_approval_seconds`; NULL there means "not tracked" (workflows from before migration 0006), never zero.
- **Downtime (`downtime/`, ADR-002 item 6, `docs/runbooks/downtime.md`):**
  - Read-only mode is an open `downtime_periods` row per tenant (admin: `POST /api/downtime/start` / `end`), so every serverless instance sees it; `READ_ONLY_MODE=true` forces it everywhere. `downtime.service.enforce_read_only` is a dependency on the whole `/api` router: it refuses POST/PUT/PATCH/DELETE with 503 and `X-Read-Only: true` before the route runs, reading the tenant from the bearer token or the API key prefix. Exempt: `/api/auth/*` and `/api/downtime/end`. A new write route is covered automatically (`tests/test_downtime.py` walks every route); a new exemption goes in `EXEMPT_PATHS`.
  - `GET /api/census` (JSON or CSV) is a PHI read: one `PHI_READ` entry per request.
  - Backfill: `PUT /api/tasks/{id}/backfill` and `PUT /api/workflows/{id}/complete` with `completed_at` record paper work at the time it was done, which must fall inside a recorded period (`downtime.service.backfill_period`); `backfilled_at` marks such rows. Outages nobody switched read-only for are recorded afterwards (`POST /api/downtime/periods`).
  - Frontend: `useReadOnly()` (polls `/downtime/status`; a 503 with `X-Read-Only` refetches it) disables write controls; `DowntimeBanner` in `AppLayout`; `/census` prints with `print:` styles.

- **Escalations (`escalations/`, ADR-002 item 12):**
  - `service.run_tenant` escalates overdue tasks of one tenant in the caller's transaction: level 1 at the SLA target (`analytics.service.TASK_SLA_HOURS`) to the assignee or assigned role, level 2 after `POLICY`'s further interval to `SUPERVISOR_ROLE`. One `escalations` row per (task, level), unique, so runs are idempotent; at most one new step per task per run; bounded per run. Postgres takes a per-tenant advisory lock (`already_running` skips). Read-only tenants are skipped. Each step is audited (`ESCALATE_TASK`), each page attempt too (`PAGE_ESCALATION`).
  - Triggers: `GET /api/escalations/run` (Vercel Cron, `crons` in `vercel.json`, `CRON_SECRET` bearer, all tenants via `run_all_tenants`, one session per tenant from `get_session_factory()`), `POST` the same path (cron secret, or `escalation:run` by API key or signed-in admin, own tenant), `python -m app.cli escalate`.
  - `escalations/pager.py`: the `Pager` interface (`NoopPager` default, `WebhookPager` HMAC-signed, `Page` is the whole payload). In-app notifications are always sent. Pages and notifications carry no PHI (no task title): adding a field to `Page` sends it out of the app. Tests swap the pager with `run_tenant(pager=...)` or `set_pager()`.
  - `notify_role` returns how many users it notified and takes `type_`.

- **Capacity board and beds (`capacity/`, ADR-002 item 17):**
  - `bed_turnovers`: one row per turnover of a bed (unit + room string; no bed master), `dirty` -> `cleaning` -> `available` (`cancelled` when an A13 undoes the discharge before cleaning starts). A partial unique index allows one open turnover per bed. `capacity/beds.py` opens them and imports no feature module, so callers can use it: `bed_vacated(db, encounter)` wherever a stay closes (`complete_discharge`, `record_external_discharge`, `patients.service.sync_encounter`, ADT A03 without a workflow) and `mark_dirty(..., "transfer")` on A02. A new code path that closes an encounter must call it too.
  - Unit scope by the row's own `unit_id` (`rls.UNIT_SCOPED_LOCATION_TABLES`, `LOCATION_VISIBLE`), not through a patient. `encounter_id` is kept only to undo a cancelled discharge and is never returned (`__api_exclude__`).
  - `service.board` counts per unit and hour (hospital time); the hour is the active workflow's `estimated_discharge_time`, since the plan has a date only. It is an operational view, so small counts are not suppressed, but it carries no patient-level data. `capacity:read` reads it; `bed:manage` (nurse, the EVS system as an integration client, admin) advances beds, signed in or with `X-API-Key` (`router.bed_actor`).
- **Outcome analytics (`analytics/outcomes.py`, ADR-002 item 19, `GET /api/analytics/outcomes`):** length of stay against the final expected date, expected-date accuracy (final and first: `encounters.first_expected_discharge_date`, set by `planning.update_plan` the first time a date is given, NULL before migration 0019), delay-reason Pareto, discharge before noon and 30-day readmissions (only discharges with a full 30 days of follow-up count), overall and by unit code. Kept apart from `analytics/service.py` and not fed to the insights model. Same no-PHI and small-group rules.

- **SMART on FHIR EHR launch (`interop/smart.py`, `interop/smart_router.py`, ADR-002 item 14):**
  - The per-tenant allow-list is `smart_issuers` (admin, `/api/smart/issuers`): `iss`, the public client id and redirect URI the EHR registered, and `mrn_system`/`mrn_authority`/`visit_system` (which FHIR identifiers are our MRN, with the HL7 assigning authority of the blind index, and the PV1-19 visit number). A launch from any other `iss` is refused before anything is fetched from it. Like the Google login, launches use `DEFAULT_TENANT_ID`.
  - Flow: `/launch?iss&launch` (frontend `pages/SmartLaunch.jsx`, PKCE verifier in sessionStorage) → `POST /api/smart/launch` (discovery from `{iss}/.well-known/smart-configuration`, a `smart_launches` row with the state's SHA-256, the S256 challenge and a nonce) → the EHR's authorize endpoint → `/launch?code&state` → `POST /api/smart/token` (single use, verifier checked, code exchanged, id_token verified against the server's `jwks_uri`). Both POSTs are public and exempt from read-only mode.
  - The person: an `ehr_user_links` row for (`issuer`, `fhirUser`), else the email from the id_token or the `fhirUser` resource's telecom, through `identity.service.match_or_register` (same rules as the Google login; a link is recorded). A `pending` user gets a session but no patient lookup and no stored EHR token.
  - The patient: the EHR `Patient`'s MRN identifier → `adt.find_patient` (blind index); the encounter by visit number (decrypted compare), else the active stay. No match still signs in.
  - The EHR access token is never sent to the browser or logged: ciphertext under the launch's own data key (AAD: launch id + field), with the EHR patient/encounter ids, lifetime `expires_in` capped at 1 h, no refresh token. Only the DischargeFlow session that made the launch may use it (`smart.active_launch` matches `session_id`). Expiry, a 401 from the EHR, or disabling the issuer drop the ciphertext and key (`smart.end_launch`). Never return or log `access_token`, `dek`, `ehr_patient`, `state_hash`, `code_challenge` or `nonce` (`__api_exclude__`). The `httpx` logger is set to WARNING because it logs outbound URLs.
  - Every request to an EHR goes through `fhir_client.http_client()` (tests swap it for an `httpx.MockTransport` fake EHR; `tests/test_smart.py`, `e2e/smart-launch.spec.js`). `FhirClient` only requests URLs on the launch's `iss` and does not follow pagination links elsewhere.
- **EHR clinical context (`interop/fhir_client.py`, ADR-002 item 15):** `GET /api/smart/clinical-context/{patient_id}` reads active `MedicationRequest`, `Condition` and `AllergyIntolerance` live with the session's launch token, caches the parsed lists for 60 s per process (never persisted) and audits each response as a `PHI_READ`. Summaries get the same lists through a hook: `app.main` registers `smart.summary_context` with `ai.service.set_clinical_context_source` (nothing may import `interop`), and `ai.service.summary_facts(..., ehr)` adds de-identified `ehr_active_medications`, `ehr_problem_list` and `ehr_allergies` (prompt `discharge_summary@v2`). `check_grounding` then grounds against them and adds an `allergy` warning for a discharge medication named like a recorded allergy. Golden-set cases with `ehr_context` cover reconciliation and de-identification of EHR text.
- **Logging (`core/observability.py`):** never log patient fields, request bodies, prompts or model output. Log lines are JSON in production with `request_id`, `tenant_id` and `user_id` attached automatically, and a PHI scrubber redacts emails, phones, SSNs, MRNs and dates as a backstop. Pass structured fields with `extra={...}`.

## Frontend architecture
- Vite (`vite.config.js`); JSX lives in `.jsx` files. `package.json` is `"type": "module"`, so Tailwind/PostCSS configs are `.cjs`.
- **Routing (`App.jsx`):** one URL per screen, each lazy-loaded: `/dashboard`, `/patients`, `/patients/:patientId`, `/workflows/:workflowId`, `/tasks`, `/insurance`, `/assistant`, `/census`, `/plans` (daily plan review), `/instructions/:instructionsId/print` (approved patient instructions), `/launch` (SMART EHR launch: neither public nor protected, it signs in itself), `/capacity` (capacity board), `/analytics`, `/insights` (admin), `/admin` (admin), all inside `pages/AppLayout.jsx` (sidebar + header + `<Outlet>`). `RoleRoute` keeps people off screens their role can't use; the API still enforces permissions. Notification links (`/patients/:id`, `/workflows/:id`) are real routes. If the URL hash contains `session_id=`, `AuthCallback` renders before routing runs. A new screen is a route in `App.jsx` plus a `NavLink` in `Sidebar.jsx`.
- **HTTP (`lib/api.js`):** the only client. `api.get('/patients')` adds the base URL, credentials, the in-memory bearer token, and refresh-and-retry on 401. Never import axios directly or build URLs from env vars in components. `errorMessage(error)` reads FastAPI's `detail`.
- **Server state (`lib/queries.js`):** TanStack Query hooks (`usePatients`, `useWorkflow(id)`, ...) with hierarchical `keys`. Views read through hooks instead of fetching into `useState`. After a mutation, `await` an invalidation (`invalidateDischarge()` for anything that moves workflows, tasks, patients or notifications) before clearing loading state, so controls don't flicker back to stale values.
- **Live notifications (`lib/notificationStream.js`):** `useNotificationStream()` (mounted in `AppLayout`) reads the SSE stream with `fetch` so the token stays in a header, invalidates `keys.notifications` on each event, reconnects when the server ends a stream and backs off on errors. `useNotifications` polls every 30 s only while the stream is not live.
- Tests: Vitest + Testing Library (`src/**/*.test.jsx`, mock `api` with `vi.spyOn`), Playwright in `e2e/` (sign in with `signInAs(page, role)`, which uses the dev login).
- UI: shadcn/ui (Radix) components in `components/ui/`, Tailwind, a forced dark theme, lucide icons and Recharts. The `@/` alias points to `src/`. Design tokens are in `design_guidelines.json`.

## Deployment notes
